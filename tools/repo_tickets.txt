Title: Binary extended float fallback writes incorrect 80-bit layout
Issue: #19
Status: closed
Labels: bug
Body:
In `Delphi.Forms.BinaryWriter.pas` lines 216-221, the fallback path for
vaExtended when `ExtendedRawBytes` is not set writes 8 bytes of Double

Title: Collection item class name detection ambiguous for edge cases
Issue: #22
Status: closed
Labels: bug
Body:
In `Delphi.Forms.Parser.pas` lines 428-444, the parser distinguishes
between a class name and a property name after `item` by looking ahead:
if the next identifier is followed by `=`, it's a property name; otherwise
it's a class name.

This works for well-formed DFM files from the Delphi IDE, but is ambiguous
for malformed input:

```
item SomeWord
end
```

The parser treats `SomeWord` as a class name, but it could be a malformed
property without a value. This matches Delphi's own behavior (Delphi also
treats the first identifier after `item` as a class name if no `=` follows),
so it's correct for valid DFM files.

However, the lookahead logic has a subtlety: after advancing past the
potential class name and skipping trivia, if the stream hits EOF or a
non-`=` token that isn't a property start, the code treats it as a class
name without further validation.

## Scope

- [ ] Add a comment documenting the grammar ambiguity and design decision
- [ ] Consider validating that the detected class name starts with 'T'
  (Delphi convention) as a heuristic, or leave as-is with documentation

## Acceptance criteria

- [ ] Behavior documented in code comments
- [ ] No regression in existing tests

Title: BinaryWriter WriteShortString silently truncates strings over 255 bytes
Issue: #23
Status: closed
Labels: bug
Body:
In `Delphi.Forms.BinaryWriter.pas` line 64, `WriteShortString` casts the
ANSI byte length to `Byte` without validation:

```pascal
Buf := TEncoding.ANSI.GetBytes(S);
WriteByte(Byte(Length(Buf)));  // truncates if > 255
```

If `Length(Buf) > 255`, the cast silently wraps (256 becomes 0, 257 becomes
1, etc.). The written length won't match the actual data, corrupting the
binary stream.

This affects component names, class names, property names, identifier values,
and set item names -- all of which use ShortString encoding in the TPF0
format.

In practice, Delphi component names rarely exceed 255 bytes, but property
names like deeply qualified dotted names or very long identifier values
could theoretically hit this.

## Scope

- [ ] Add validation: raise if `Length(Buf) > 255`
- [ ] Add test verifying the exception

## Acceptance criteria

- [ ] WriteShortString raises a clear exception for strings > 255 bytes
- [ ] All existing tests still pass

Title: FormStats utility -- component and property statistics across a codebase
Issue: #25
Status: closed
Labels: enhancement
Body:
Add a FormStats console utility analogous to TokenStats in delphi-lexer.
Scans one or more .dfm/.fmx files and reports aggregate statistics useful
for scoping migration effort, auditing component usage, and identifying
complexity hotspots.

## Features

- Accept a single file, a directory, or a directory with `--recursive`
  to scan an entire codebase
- Auto-detect text vs binary format per file
- Report per-file and aggregate statistics:
  - File count (text vs binary breakdown)
  - Total components (objects) and unique class names
  - Total properties
  - Maximum and average nesting depth
  - Value type distribution (how many fvInteger, fvString, fvSet, etc.)
  - Object kind distribution (object vs inherited vs inline)
  - Top N most-used component classes (e.g. TLabel: 142, TButton: 98)
  - Top N most-used property names (e.g. Left: 500, Caption: 320)
- Output formats: text (default) and JSON (`--format:json`)
- Exit code 0 on success, 1 on bad params, 2 on any parse failures
  (continue scanning, report failures at end)

## CLI

```
FormStats <file-or-dir> [options]

Options:
  --recursive           Scan subdirectories
  --format:<name>       Output format: text (default) or json
  --top:<N>             Number of top classes/properties to show (default 10)
  -?, --help            Show help
  -v, --version         Show version
```

Issue: #31
Status: closed

Body:

```pascal
try

end;
```

```pascal
TFormNormalizeRule = (
  nrRemoveExplicitBounds,    // ExplicitLeft, ExplicitTop, ExplicitWidth, ExplicitHeight
```

Title: Visitor pattern for AST tree traversal (Delphi.Forms.Visitor)
Issue: #41
Labels: enhancement
Body:
Multiple library units independently recurse through the `TFormFile` AST:
`NormalizeForm`, `ComputeStatistics`, `FormObjectToJSON`, and future units
like `EnumComponentReferences` and `CompareForms`. Each reimplements the
same object/property/children/collection-items traversal.

A standard visitor interface centralizes the walk and lets consumers focus
on per-node logic without boilerplate recursion. It also opens the door to
composable analyses (run multiple visitors in a single pass).

## Design

```pascal
IFormVisitor = interface
  procedure VisitObject(Obj: TFormObject; Depth: Integer);
  procedure VisitProperty(Prop: TFormProperty; Obj: TFormObject; Depth: Integer);
  procedure VisitValue(Value: TFormValue; Prop: TFormProperty; Depth: Integer);
end;

procedure WalkForm(Form: TFormFile; Visitor: IFormVisitor);
procedure WalkObject(Obj: TFormObject; Visitor: IFormVisitor; Depth: Integer = 0);
```

## Key behaviors

- Depth-first traversal: object, then its properties (with values), then
  children, then recurse
- Collection items: properties with `fvCollection` values have their
  `CollectionItems` walked as nested objects
- `WalkObject` is public so consumers can walk a subtree without starting
  from the root
- The interface uses methods rather than anonymous procs to allow stateful
  visitors (classes that accumulate results)
- A `TFormVisitor` base class with empty virtual methods is provided so
  consumers only override what they need

Title: AST navigation helpers (Delphi.Forms.Navigation)
Issue: #48
Labels: enhancement
Body:
Consumers frequently need to locate specific objects or properties in
the AST by name, class, or dotted path. Every consumer currently
reimplements these lookups with ad-hoc recursion. A dedicated navigation
unit provides these as reusable, tested building blocks.

Separate from `Delphi.Forms.Types` to keep the core types unit small
and focused on data structures.

## Design

```pascal
function FindObjectByName(Root: TFormObject; const Name: string): TFormObject;
  // Case-insensitive recursive search. Returns first match or nil.

function FindObjectsByClass(Root: TFormObject; const ClassName: string): TArray<TFormObject>;
  // Case-insensitive recursive search. Returns all matching objects.

function FindProperty(Obj: TFormObject; const Name: string): TFormProperty;
  // Case-insensitive search of Obj.Properties only (not recursive).
  // Returns first match or nil.

function FindPropertyByPath(Root: TFormObject; const Path: string): TFormProperty;
  // Resolves dotted path like 'Memo1.Font.Color':
  //   - Navigate to child named 'Memo1'
  //   - Find property 'Font.Color' (dotted property name)
  //   - If 'Font.Color' not found as a single property name, try
  //     navigating 'Font' as a child and finding 'Color'
  // Returns nil if any segment is unresolved.

function EnumAllObjects(Root: TFormObject): TArray<TFormObject>;
  // Flattened depth-first list of all objects in the tree (including Root).

function EnumAllProperties(Root: TFormObject): TArray<TFormProperty>;
  // Flattened list of all properties from all objects in the tree.
```
